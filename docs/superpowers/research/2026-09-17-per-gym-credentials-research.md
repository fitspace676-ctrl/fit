# Per-gym credentials (T1.25) — research

Snapshot at `origin/main` (`ac59b682`, 2026-09-17), read in worktree `../fit-auth`
(`feat/per-gym-credentials`). No code changed — research only.

## Decision this research assumes (recap)

`User` stays the cross-gym identity (email `@unique`, push tokens, notifications).
A new per-gym credential (table TBD — see §5) carries password, `emailVerified`,
name and phone **per membership**. Signup on an existing email → normal signup
with its own password, gym-scoped verify mail, no enumeration. Staff invite on an
existing email → accept-invite sets a new password for that gym. Superadmin
`registerGym` on an existing owner email → new gym's credential + activation
mail instead of `409`. Reset/verify/login/refresh resolve only the host gym's
credential; a tenant-less host picks a gym. Google/Apple: identity → `User`,
credential per gym. Migration is additive + backfill; `User.passwordHash` is not
dropped yet.

## 2. Schema (`packages/db/prisma/schema.prisma`)

- **`User`** (`:491-531`): `id`, `email @unique`, `name?`, `phone?`, `passwordHash?`,
  `emailVerifiedAt?`, `googleId? @unique`, `appleId? @unique`, `isSuperAdmin`,
  `tokenVersion` (`@counter`, session-invalidation), timestamps. Relations:
  `memberships GymMember[]`, `refreshTokens`, `pushTokens`, `carts`,
  `notifications`, `notificationPreferences`, CRM relations.
- **`GymMember`** (`:643-...`, unique `@@unique([userId, gymId])`): `role`,
  `status`, `joinedAt`, `kindOverride`, `deletedAt` (soft-delete/trash),
  directory profile extras (`dateOfBirth`, `gender`, `address`,
  `emergencyContactName/Phone`, `medicalNotes`, `tags`, `personalId`,
  `startDate`), **`firstName?`/`lastName?`** (`:715-717`, already per-gym, but
  only populated for login-less directory staff today), `locationId?` (home
  branch), `assignedLocationIds` (`@deprecated`, Stage 6 shadow). No credential
  fields at all — this is the natural home _or_ the natural sibling for a new
  `GymCredential`.
- **`RefreshToken`** (`:2233-2250`): `userId`, `gymId?` (nullable, no FK — a
  gone gym just invalidates the pin), `tokenHash @unique`,
  `deviceFingerprint?`, `familyId`, `revokedAt?`, `expiresAt`. Indexed on
  `userId`, `gymId`, `familyId`.
- **`StaffInvite`** (`:2261-2275`): `gymId`, `email` (lower-cased), `role`,
  `token @unique`, `expiresAt`, `usedAt?`. No password field — the invitee
  chooses one at accept time via register/login, which is exactly where a
  credential would be created.
- **No `EmailVerificationToken` / `PasswordResetToken` models exist.** Both are
  Redis-only, single-use, TTL'd keys (`VERIFY_KEY_PREFIX`/`RESET_KEY_PREFIX` in
  `auth.service.ts:56-60`, mapping `token → userId`). A per-gym version needs
  `token → (userId, gymId)` in the same Redis scheme — no new table required for
  the tokens themselves.
- **Migration style** (last 10 in `packages/db/prisma/migrations/`, newest
  first: `20260915120000_class_template_check_in_location_not_null`,
  `20260913180000_refresh_token_gym`, `20260909195523_home_banners`,
  `20260902180000_service_categories`, …): one directory per migration,
  `YYYYMMDDHHMMSS_snake_case_name`, a prose comment block at the top explaining
  _why_ (not just what), then the SQL. `20260913180000_refresh_token_gym`
  (full text) is the closest precedent — additive, nullable, **no backfill**,
  old rows keep old behaviour until they rotate. `20260814110000_staff_trainer_link`
  is the precedent for a migration that _does_ backfill with real data
  (creates login-less placeholder `User`+`GymMember` rows via `gen_random_uuid()`
  and raw SQL `INSERT ... SELECT`) — the shape T1.25's "password/verify copied to
  every existing membership" backfill should follow.

## 4. Recommendation: `GymCredential` table vs. columns on `GymMember`

**A new `GymCredential` table**, not columns on `GymMember`, for three reasons:
(1) `GymMember` is created in several places that have no password yet
(directory-staff add, invite-before-accept) — a credential is optional-until-set
in a way that sits awkwardly as nullable columns on a row that otherwise means
"this person belongs to this gym"; (2) the reset/verify Redis tokens
(`resetKey`/`verifyKey`) resolve to _a credential_, and a dedicated table with
its own `id` gives those tokens a clean foreign key instead of a composite
`(userId, gymId)`; (3) it mirrors the existing `RefreshToken.gymId`
precedent — "this piece of the session/credential story is pinned to one gym" is
already a first-class pattern in this schema, not a new one. Columns on
`GymMember` would work too and cost one less join, but blur "membership" and
"credential" onto one row that migrations already load-bear heavily (see the
`locationId`/`assignedLocationIds` comment block, `:718-807` — this model has a
track record of collecting meanings that later need separating).

**Biggest risk, by a clear margin: `POST /auth/login` with no resolvable gym.**
Today `login` takes an _optional_ `gymSlug` and falls back to the primary gym
because one password answers for the whole person. Per-gym credentials make the
gym the join key for _which password to check_ — there is no "check the
password, then figure out the gym" order anymore. `apps/admin` and gym-subdomain
web logins are fine (host always names the gym). The two genuinely hard cases:
**`apps/mobile`**, where `resolveGymSlug()` (`session.ts:353-363`) explicitly
falls through to `undefined` for a multi-gym build with no deep link and no
prior login — that path has no gym to check a password against and needs a
client-side "which gym" step that doesn't exist today; and **`app.<root>` /
platform-wide login** (mentioned in the decision as needing "gym selection"),
which today resolves to the user's earliest-joined membership and would need an
explicit picker or an email-first-then-gym-list flow. Second-biggest risk:
`revokeAllForUser` (`token.service.ts:368-373`) revokes **every** refresh token
across **every** gym on a password reset — correct today (one password, one
compromise = compromise everywhere), questionable once passwords are per-gym
(should a Downtown password reset log the person out of Riverside?).
